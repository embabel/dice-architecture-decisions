# Record confirmed world changes as supersessions

Pro and Basic can both describe the same account at different times. Store a confirmed world change as two linked proposition occurrences with an explicit handoff in valid time. Reserve the existing contradiction path for competing claims and retain its behavior for existing consumers.

## Context

That branch supplies no new validity window or lineage. Pinned originals stay intact. ## Decision

Make durable world progression an opt-in revision policy. The conflict detector supplies a classification. The application supplies authority to apply the change, a trusted effective instant, and a stable transition identity. The reviser prepares both writes against the same context. A transaction-aware writer validates the expected predecessor and applies the pair.

The first implementation exposes a SQLite writer for an application that has already accepted a
trusted event. The writer prepares the two records and commits them with their audit entries.
The automated revisers continue to return their existing results. [SQLite implementation](https://github.com/embabel/dice/pull/246)

For an accepted transition effective at `T`, the two rows record:

| Row | Stored status | Valid-time fields and lineage |
| --- | --- | --- |
| Previous Pro occurrence | `SUPERSEDED` | Keep its known `validFrom`. Set `validTo = T`. Preserve its existing lineage, provenance, and confidence. |
| New Basic occurrence | `ACTIVE` | Set `validFrom = T`. Keep its known end, otherwise leave it open. Add the previous occurrence ID to `supersedes`. |

Use the existing half-open interval rule. If the previous start is unknown, leave it unset. At `T` the predecessor’s window has closed and the successor’s has begun. Reserve `invalidatedAt` for retraction. Preserve observation times separately from effective times. [TemporalMetadata](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/temporal/TemporalMetadata.kt#L21-L73)

Use an explicit effective instant from the source when the host trusts it. A host may designate an authoritative receipt time as effective for a specific feed. A tie in detector recency, a model answer, or a storage timestamp alone supplies insufficient authority. Route ambiguous dates, conflicting existing bounds, out-of-order changes that cross a committed successor, future changes, and pinned predecessors to a host decision or scheduling workflow. Keep `Revision`, ordinary disagreements, and the detector’s default predicate set on their existing paths.

## Evidence and persistence

Keep the public `RevisionResult.Contradicted` type and its `conflictType`. Successful opt-in materialization carries a `SUPERSEDED` original and the successor with explicit lineage. The converter can present those stored values directly. Keep its legacy presentation for results using the old path. Route a proposal awaiting approval separately so it cannot appear as an accepted replacement. [EvidenceConverter](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/evidence/EvidenceConverter.kt#L224-L261)

A current scoped read uses active claims and their validity. A historical valid-time read uses the stored intervals, including linked superseded predecessors, and omits unresolved contradictions. An audit read answers what the application had recorded at a transaction time and requires a complete baseline. For example, a downgrade effective Monday and recorded Wednesday changes the valid-time answer from Monday and the audit belief from Wednesday. Use the temporal predicate for the validity window. The existing confidence calculation only takes the dated path when `validFrom` exists. [Confidence calculation](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/proposition/Proposition.kt#L474-L493) · [Audit guide](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice-user-guide/src/main/asciidoc/features/audit-history.adoc#L31-L57)

When an automated pipeline adopts this policy, treat both retired statuses as terminal for in-run candidate selection and final-copy precedence. The pipeline already includes both sides of a `Contradicted` result in the write set. Its special handling for retired copies currently recognizes only `CONTRADICTED`. The writer must keep the predecessor, successor, and audit updates in one atomic unit. A retry with the same transition identity must be idempotent. Both sides use one audit timestamp so replay cannot reconstruct half of a committed transition. [In-run candidate filter](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/proposition/revision/LlmPropositionReviser.kt#L522-L533) · [Persistence plan](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/pipeline/PropositionResults.kt#L76-L117) · [Terminal copy predicate](https://github.com/embabel/dice/blob/0a06b37fb36e921d9b13f975bd56f3961244fe47/dice/src/main/kotlin/com/embabel/dice/pipeline/PropositionResults.kt#L391-L398)

The Drivine mapper already round-trips temporal fields and the audit record already captures them. The missing durable capability is occurrence identity. The default Drivine uniqueness constraint and duplicate lookup collapse the same text in one context regardless of status. A second Pro period needs its own ID and window. Give opted-in occurrences a stable version key distinct from text, carried through duplicate recovery and audit canonical lookup. Keep ordinary rows on the current context-and-text identity. An adapter may enable the policy only when it can preserve both identities and commit the transition atomically. ## Compatibility and rollout

- Preserve existing IDs, status names, timestamps, and audit records. A legacy `CONTRADICTED` row can represent either case. Backfill only from verified source records that establish the previous occurrence, replacement, and effective time. Record any repair as a new audit operation.
- Make the new policy additive. Existing callers, exact-text deduplication for ordinary facts, and the existing Decision example keep their behavior. For an enabled adapter, migrate uniqueness and canonical lookups before enabling writes. Stop older writers from sharing enabled contexts since they still deduplicate across occurrences.
- Start with Drivine on SQLite. Enable the startup setting on every writer, back up the database, and migrate with writes stopped. Retain the unique proposition ID and replace the text constraint with the repository's exact-text lookup under SQLite's write transaction. An ordinary save attaches new evidence to the active matching occurrence when one exists. An older release requires the pre-migration backup or reconciliation of repeated occurrences before reinstating the old constraint.
- Gate expansion on adapter conformance. Other adapters keep the existing revision path until they can preserve occurrences and commit both writes. Keep Prolog, decay algorithms, unrelated revision paths, and the default detector configuration outside this change.

## Acceptance cases

1. A confirmed Pro-to-Basic transition stores Pro as `SUPERSEDED`, closes its window at the effective instant, and links Basic back to Pro. Before the boundary the scoped valid-time answer is Pro. At the boundary it is Basic. A store reload and transaction-time audit preserve both records.
2. Annual versus monthly billing remains a stored `CONTRADICTED` case with conflicting evidence and no supersession interval or link. A pinned, ambiguously dated, or stale predecessor receives no automatic supersession.
3. A repeat delivery creates one transition. Pro to Basic to Pro creates three occurrences with distinct windows. A failed second save rolls back the entire transition and its audit records.
4. Legacy fixtures and readers work without a backfill or a new result subtype. Scope enforcement also applies when following predecessor links.
5. Before adopting the policy in the automated pipeline, verify that ordered and batched results cannot replace a retired occurrence with its earlier active copy.

Review the decision before adopting the SQLite writer. Keep the storage contract as the gate for each additional writer.
